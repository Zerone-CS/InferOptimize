# 干预设计、执行与回退契约

optimize 拥有变更计划和实际动作记录。设计、执行、回退是独立可委托的能力，不因生成计划便自动实施，也不因建议回退便声称已恢复。本文是工作记录约定，不是自动部署器或已实现的机器状态机。

## 1. 公开输入与输出

| 能力 | 最小输入 | 输出 | 返回边界 |
|---|---|---|---|
| 设计 | 目标/约束、可信基线或明确缺口、假设/证据引用、当前配置/源码身份、分配预算 | 变更计划、实验矩阵、验证/回退步骤、前置条件与证伪分支 | prepare 只准备；不启动压测或修改服务 |
| 执行 | 已确定的计划及 hash、当前目标实例身份、允许动作、排他安排和生效判据 | 实际 diff、配置/构建身份、完整日志、退出码、生效证据与未完成项 | execute 只实施委托动作；计划前提失效返回协调者 |
| 回退 | 指定计划/执行引用、目标实例、上一可用配置/构建、允许恢复范围 | 实际恢复动作、日志、恢复后身份和核验结果 | 回退失败与未执行分别记录，不凭建议标记成功 |

按 [任务契约](../../references/suite_contract.md) 接手与返回；历史 role=design 继续使用，goal 明确本次能力，mode 限定动作范围。独立任务由当前 agent 协调其请求范围，无需先调用完整主流程。

输入消费 evaluate 的 [测量与报告契约](../../evaluate/references/records.md)、diagnose 的 [账本/假设](../../diagnose/references/records.md)，必要时使用 knowledge 的 [固定快照查询结果](../../knowledge/references/records.md)。不导入这些模块内部实现，也不读取其临时分析目录。可直接处理用户给定且证据充分的变更，不要求为满足流程形式再跑一次诊断。

## 2. 给每个动作写预测与证伪条件

每张候选卡必须记录：target 因子、作用机制、前置条件、变更集、预期正向和负向变化。
另记最终 X_out/完成时间预测、机制信号、证伪结果、保护指标、回退方式和预算。
例如扩实际 batch 预计 N_B/K 上升，也可能使 tau、KV 压力及 p99 上升；只预测分子是不完整的。
参数、图、算子、调度、通信及代码变更都核对实际路径，不能把配置解析成功当生效证据。
必要依赖合并登记为依赖束；保护场景同用实际候选部署，不拼接不同配置的有利结果。
按契约配对/交错重复，分别判断数据、质量/SLO、效果和机制；正式收益由关闭重型 profiling 的运行比较。
实验后返回执行记录及评估所需原件；diagnose 更新局部 ledger/机制判断，协调者维护候选队列和基线。正负结果均先入 campaign，再按 knowledge 流程审阅为知识增量。

## 3. 实验单位与配置审计

实验单位是完整的一次 benchmark run；逐请求样本用于时延分布，不能假装成许多独立服务重复。
对照时保存完整启动 argv、配置、环境与源码指纹，并定义 expected_config_diff。

| 变更形式 | 允许的结论 |
|---|---|
| 单个参数且其他状态可比 | 该参数的整体效果；机制仍需中间证据 |
| 主变更加必要依赖 | 依赖束的整体效果；不能归功于其中单项 |
| 多个优化组合 | 组合在所测条件下的效果；有成本预算时做消融分配贡献 |
| 同时更换负载/版本/输出规则 | 重新建立基线或明确不可直接归因 |

启动后比较“请求值—解析后值—运行路径”。有意变更、必要依赖、自动派生项分别记录。
非预期差异先解释；无法控制时保留探索结果，不纳入单项因果结论。

## 4. 变更计划

为每个候选保存计划身份及版本/hash，并至少写明：

- hypothesis_ids、baseline 引用、作用范围、target_factors 和证据/知识来源。未知机制保留未知；受控干预可用于鉴别，不要求唯一瓶颈已证实。
- 完整 expected_config_diff：参数/必要环境、代码 diff、构建/包身份、图/算子路径及部署范围。主变更、必要依赖和自动派生项分开；代码变更有可复原身份。
- 可比条件：负载与客户端策略、输出/成功/窗口契约、环境、参考输出及 hash。改变任务语义/版本/计量规则时明确需要新基线，不伪装成原单项对照。
- 实验矩阵按目的明确范围：用于采纳的验证安排 baseline/candidate、配对/交错顺序、全部重复、全部保护场景、质量检查、停止条件和独立确认；相同 candidate 部署接受全部场景，正式计分关闭重型 profiler。预算内的鉴别/探索可只设计最小试验，仍遵守质量与服务硬约束，并明确结果不能用于采纳；完整验证和独立确认列为后续条件，未执行项保持未决，不因此扩大本次预算。
- 验证输入与观察：最终指标、机制信号、预期正负变化、证伪分支、实际生效判据及受保护质量/SLO/资源指标。指标不被现有工具支持时先验证扩展，不能只换名称。
- 精确回退步骤、上一可用配置/构建、恢复核验方法、预算及执行条件。可预先委托计划内的失败恢复，不把回退扩展成清理未知进程或更改宿主环境。

质量/噪声/收益判据由 evaluate 的 [验证方法](../../evaluate/references/validation.md) 维护，计量定义由 [测量契约](../../evaluate/references/measurement_contract.md) 维护；本模块在计划中引用固定版本，不另设较宽标准。

## 5. 执行记录与失败返回

执行前核对计划 hash、授权范围、目标容器/PID/start time、设备、端点及当前配置；相同端口或 PID 数字不能替代实例身份。保存原配置和回退材料，再按已委托计划实施。

每个实际动作记录时间、argv 或操作说明、输入/输出路径/hash、退出码、stdout/stderr、实际 diff 和副作用。核对“请求值—解析值—运行路径”，配置被接受不等于生效。计划内步骤未执行明确标记，不能把命令草案写成执行结果。

计划条件不成立、出现非预期差异或执行失败时保留现场及已发生动作，执行已委托的计划内恢复；需要扩大范围时返回协调者调整，不自行新增变更、服务操作或总预算。部分执行也必须报告实际部署状态，避免后续评估把旧配置当候选。

回退另记所恢复版本、实际动作与恢复后核验，区分 planned / not_run / completed / failed 等状态语义。只有核对实例、配置/代码身份和约定健康证据后才报告完成；这些是记录状态，不宣称已有自动工具验证。

## 6. trials 与评估交接

trial 记录至少保存：

- trial_id、hypothesis_ids、计划引用、baseline/candidate run IDs、workload hash。
- 计划和实际 config diff、主变更/依赖束、动作类型、代码/构建/安装源身份、预期正负因子变化与实际生效证据。
- 实验顺序及全部重复引用；evaluate 的质量/SLO、效应估计、不确定性和比较报告；diagnose 的实测因子及机制报告。
- 参考/候选输出 ID/hash、比较器 argv、退出码与完整日志；不覆盖基线参考。
- data_validity、quality_slo、performance_effect、mechanism、decision 分别引用负责方记录；decision 和当前基线由协调者提供，不由本模块写入全局状态。
- 回退计划、实际回退结果、未解决问题和下一动作。候选未采纳也保留可复用证据。

计划、执行、回退产物分别封存并互相引用。optimize 向协调者交付实际记录与评估所需输入，不自动启动 evaluate；evaluate 返回收益/守卫评估后，由协调者作 adopt/revert/defer 及基线更新。
