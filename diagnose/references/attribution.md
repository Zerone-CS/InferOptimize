# 证据归因与竞争假设

本文件用于因子观测后的机制判定和鉴别建议。先按 [因子驱动诊断](factor_diagnosis.md) 从定义建立观测表，
完成实际数据字段映射；由因子变化和限制证据选择本文件中的鉴别方法。

## 1. 先回答“现有数据允许说什么”

证据强度按具体结论判定，不用统一的“确定/不确定”标签替代推理。

| 证据 | 可以支持 | 不能单独支持 |
|---|---|---|
| 配置/源码 guard | 在该版本、输入条件下是否允许某路径 | 运行中每一步是否走过该路径、吞吐收益 |
| 时间线和计数 | 观察到哪些活动、结果与时间分布 | 只凭占比断定可消除成本或唯一根因 |
| 基线/候选对照 | 在已控制条件下变更的性能效果 | 变更影响多个机制时其中哪一个贡献多少 |
| 机制信号与消融 | 特定机制的预测得到支持或反驳 | 超出所测模型、版本、负载的普遍结论 |

历史 profiling 只能为新 campaign 生成候选。记录其 run_id、模型、版本、实际配置、
负载和采集窗口；缺少匹配证据时不得称“当前通信占 58.8%”等当前事实。
在本轮未采集过 trace 时明确写“沿用历史假设，尚未在当前配置验证”。

## 2. 一张假设卡对应一个可区分的问题

```text
hypothesis_id:
scope: model/hardware/version/workload/config_hash
observations: run_id + artifact_path + metric/window
target_factors: 因子ID、对应ledger及观测/缺口
claim: 哪个约束或依赖怎样影响目标指标
alternatives: 能产生相同观察的其他解释
missing_evidence: 缺少什么，已有数据能否补算
intervention: 改动与必要依赖
predicted_outcome: N_Y/T、约束指标预计怎样变化
predicted_mechanism: 哪个中间信号预计怎样变化
factor_tradeoffs: 各相关因子的预期方向、可能反向变化及净效果计算条件
falsification: 什么结果会反驳本解释
cost_and_dependencies: 重启/采集/时间/资源及阻塞
```

例：高并发吞吐平台且 ITL 上升，只支持“在该负载下吞吐不再增长”。
竞争解释包括图回退、KV/调度限制、计算/带宽/通信饱和、排队与负载构成变化。
选择能区分解释的数据，如实际图键和回退次数、KV 分配失败原因、调度输入、
多 rank 时间线；不要因历史常见就跳到“扩图肯定有效”。

## 3. 从吞吐账本选择观测

先比较 `X=N_Y/T`。只有完整轮次和输出归属可用时，才比较 `Y_bar` 与 `tau=T/K`。
同一窗口先聚合原子总数，再求比值；逐轮简单平均的比例与按原子项加权的总量比值一般不同。
变化满足：

```text
X_candidate / X_baseline
  = (Y_bar_candidate / Y_bar_baseline) / (tau_candidate / tau_baseline)
```

这用于算净效果，不宣称因子独立。扩大实际 batch、投机长度和图范围都可能同时改变分子与分母。
固定输出总量时，优化也可能表现为轮数 K 下降；不能只比单轮时长。
输出长度改变、成功率改变或统计口径改变时，先解释这些变化，避免将任务变化误作加速。

按缺口选数据，不要求起手采齐五因子：

- 怀疑供给：计划/实际发送、客户端积压、服务等待队列、请求终止状态。
- 怀疑调度/KV：实际序列参与、调度未准入原因、token 预算、KV 分配/抢占/重算。
- 怀疑投机：接受位置、修正/额外输出、停止前后数量及完整轮代价。
- 怀疑图路径：实际输入 shape、捕获键、命中/回退、运行版本分派条件。
- 怀疑执行瓶颈：有代表性的 host/device 时间线、依赖及相关 rank；按问题选 PMU。

## 4. 时间与资源的判读边界

同一分析窗口中，对活动区间先取并集，再计算交集；汇总时注明是否跨 stream/rank。
设备空白不是天然的 host 时间，通信占比也不是天然的关键路径比例。
单 rank 很慢可能在等待其他 rank；优先区分传输、同步等待和负载不均衡。

kernel 持续时间可受计算、访存、调度、同步或低并行度共同影响。
计算受限/带宽受限假设需要匹配硬件和操作定义的指标及形状分析，
不能把权重文件大小直接当作每步实际 HBM 流量，也不能把内存分配量当读写带宽。
AI CPU 上的算子名称只用于筛查，需要确认功能、规模和路径后判断是否异常。

当多个并行分支同时约束完成时，只优化其中一个未必改善总时间。
只有收集足够依赖和资源串行关系，才用关键路径解释端到端收益。
改动后重新观测必要部分，不能用旧分解按比例预测全部净收益。
不同单位的因子不能按数值大小排序瓶颈。普通解码每次参与产出接近一个 token、正常 EOS 带来的裁剪
都可能符合算法和任务定义；优化目标是约束下的交付效率，不是把每个比例推到 1。

## 与实验设计的交接

本模块返回证据、假设、干预意图与证伪条件；完整变更计划、实验单位和配置审计由 [optimize 实验契约](../../optimize/references/experiment_contract.md) 维护。重复、噪声、质量和效果评估由 [evaluate 验证方法](../../evaluate/references/validation.md) 维护。最终去留与基线更新由协调者决定。
