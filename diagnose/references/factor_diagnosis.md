# 从吞吐定义到证据映射与因子诊断

本流程把测量契约、业务语义、profiling 和知识库接成可复核的诊断链。
先读 [测量契约](../../evaluate/references/measurement_contract.md) 与 [归因方法](attribution.md)。
目标是选择有证据、有收益可能且能证伪的下一动作；不要求先证明唯一瓶颈。

## 1. 为当前运行建立因子账本

从 [factor-ledger.example.json](../assets/factor-ledger.example.json) 建立本次账本，保存在 campaign。
`run_id`、窗口、计数规则、配置/源码身份、原始产物及派生方式必须可以互相定位。
模板仅提供记录结构，不会采集数据；未知数值保留 `null`，写明缺口与下一步。
先遍历第 3 节的整棵因子树，将已知、未知和不适用项登记，再选择补采顺序。
已有数据可重算时先重算；不能因某项未知而跳过总账，也不因未知而停止全部实验。

每项状态按该项具体主张填写，不能用一项的状态覆盖整份账本：

| 状态 | 含义与最低记录要求 |
|---|---|
| `measured` | 有直接观测；保存实际字段/事件、计数语义、范围及原始引用，不代表语义已自动核验 |
| `derived` | 从列明的观测或派生量计算；保存公式、依赖项、聚合和适用条件 |
| `estimated` | 使用抽样、代理或模型估计；保存假设、不确定范围和不可精确对账的原因 |
| `unavailable` | 当前缺失、未记录、不可关联或定义尚不成立；保存影响及可行补证动作 |
| `not_applicable` | 该场景没有此机制或该量不适用；保存版本/路径依据，不能用来掩盖漏采 |

例如实际用量是 measured，求和后的 N_Y 是 derived；由 chunk 数猜 token 数只是未经验证的估计。
估计不能回填为主账的实测 N_Y，也不能参加声称精确的因子对账。
普通解码中的“草稿接受率”可不适用，但实际序列参与和有效输出仍需按各自定义处理。
分母为零的比值保持 `null` 并注明未定义，不以 0、1 或省略项修补恒等式。

## 2. 先分开计量因子和机制解释量

基础指标始终是 `X_out = N_Y / T`，N_Y 为最终成功请求贡献的实际有效输出 token 数。
T 是契约规定的完整窗口秒数；窗口内等待、失败、空闲、编译和收尾均保留。
请求上限、chunk、padding、输入、重算和多 rank 重复计算不能替代 N_Y。
只有全部计分输出能唯一归属于 K 个完整逻辑轮时，才使用：

```text
Y_bar = N_Y / K                 tau = T / K
X_out = Y_bar / tau
X_out = (K/T) × (N_B/K) × (N_G/N_B) × (N_C/N_G) × (N_Y/N_C)
```

| 计量因子 | 本契约中的解释 | 必须核对的条件 |
|---|---|---|
| K/T | 完整逻辑轮完成数/秒 | 轮次身份和结束边界完整，分母为同一 T |
| N_B/K | 每轮实际序列参与数 | B_k 是轮内不同序列数，多次调用只计一次，N_B 为各轮之和 |
| N_G/N_B | 每次序列参与产生的停止筛选前逻辑输出数 | 接受、采样、修正和额外输出按当前算法定义，排除拒绝草稿 |
| N_C/N_G | 停止与计数筛选后的保留比例 | N_C 是 N_G 的保留子集，计数粒度一致 |
| N_Y/N_C | 最终成功请求贡献的 token 保留比例 | N_Y 是 N_C 中最终成功请求的贡献，不等于请求成功率 |

N_B 的单位是“序列参与次数”，N_G/N_C/N_Y 的单位是按相同规则计数的逻辑输出位置。
五因子连乘是总数比值的约消，不能改成各轮比值的非加权平均后仍称精确。
全式要求相关分母非零、同 run/同窗口，且输出包含关系与唯一归属已经核验。
并发/流水时 tau 是有效完成间隔，不是轮生命周期平均值，也不是某 kernel 的耗时。
即使轮串行，窗口的起步、间隙和排空仍包含在 tau 中；K=0 时不用含 K 的分解。
若 N_Y>0 却无法登记对应轮，先标轮次归属缺失，不宣称完整五因子还原。

图命中率、HBM 流量、算子时长、通信重叠、KV 抢占、host 供给等属于机制解释量。
这些量帮助解释计量因子怎样变化，不能随意追加为独立乘数，或凭占比定位唯一瓶颈。
五因子也不相互独立：增大实际 batch 或投机长度可能同时改变产出、完成间隔和失败损失。

## 3. 完整遍历因子树，再决定精测范围

首次诊断至少检查下面各分支，并给每支登记当前观察、状态、覆盖和缺口。
完整遍历要求“知道缺什么”，不要求每次把所有因子精确测完。

```text
X_out = N_Y / T
├─ 有效输出 N_Y
│  ├─ 成功请求/序列与实际输出位置、EOS/停止/截断/失败
│  ├─ 轮次 K、实际参与 B_k、prefill/解码/投机的逻辑边界
│  ├─ 接受/采样/修正/额外输出 N_G、停止保留 N_C
│  └─ 输入构成、输出长度与质量变化造成的任务差异
└─ 完整窗口 T 与轮完成速率 K/T
   ├─ 供给：计划/实际发送、客户端滞后、服务队列和空转
   ├─ 调度/KV：准入、预算、分配、抢占、换入换出和重算
   ├─ 执行路径：shape、图捕获/命中/回退、算子与融合路径
   ├─ 计算/访存：实际工作、数据流量、并行度和资源竞争
   ├─ 通信/分布式：集合通信、同步、跨 rank 等待与负载差异
   └─ host/运行时：提交、同步、编译、I/O、初始化和收尾
```

供给、KV、图路径和设备执行可共同限制完成；不要将整棵树强行二分为分子或分母根因。
记录“吞吐平台”“rank 间不均衡”等观察，再列能解释观察的竞争假设。
优先补能改变下一决策、区分竞争解释且成本可接受的数据；重复采无判别力的占比价值很低。

## 4. 把账本项映射到真实数据

每个 observations 条目至少描述：目标因子、原始文件、实际表/字段/事件名、筛选与聚合。
还要保存单位、时钟、窗口裁剪、rank/stream 范围、去重键、源码语义依据及缺失覆盖。
这里的符号是契约名称，不声称任何 msprof 导出天然含有同名列。

| 要获得的量 | 优先证据 | 现场必须核对的映射 |
|---|---|---|
| T、实际输出、最终状态 | 完整客户端记录，必要时与服务端对账 | 计分起止、实际用量来源、终态、失败部分输出处理 |
| K、B_k、输出归属 | 引擎语义日志/应用埋点 | 逻辑轮 ID、序列 ID、实际参与、提交位置、开始/结束定义 |
| N_G、N_C、停止损失 | 算法及停止处理语义标记 | 接受位置、修正/额外输出、停止前后结果，不能仅记草稿长度 |
| 图/调度/KV 解释量 | 当前源码分支、运行日志或定向埋点 | 实际 guard、命中/回退、准入原因、分配/抢占和重算 |
| 计算、通信和 host 活动 | 实际 profiler 导出及关联标记 | 事件类别、起止含义、异步关联、范围与采集遗漏 |
| 资源计数器/PMU | 当前产品与版本支持的实际采集产物 | 开关、指标定义、单位、采样/缩放、作用范围和采集扰动 |

映射以当前产物和源码为准，保存解析器版本与一次可手算的小样本核对。
以某 tensor 的第一维推 B_k、以 token budget 推输出、以 RPC 次数推 K，都需要额外语义证明。
仅有 kernel/shape 通常不足以恢复 K、B_k、接受/停止结果及最终状态；按缺口补 semantic markers。
覆盖记录包括采到的 rank/stream、事件类别、时间段、丢失/截断及预期未采范围，不能把未记录当零。
本套件不自动解析 msprof、不维护 factor ledger，也不自动添加引擎语义标记。
evaluate 的 `benchmark.py` 和 `validate_run.py` 可提供总账依据，内部因子需另行适配并核验采集器。
新增解析器先用受控样本验证单位、边界、重叠及重复处理，再用于正式归因。

## 5. 统一身份、窗口、时钟与粒度

使用 run/request/sequence/轮次/输出位置关联业务事件；标记名称和关联方式现场确认。
输出位置的逻辑唯一键按测量契约建立，不按 token ID 去重，不把 TP rank 副本重复计数。
同轮同序列多次设备调用不增加 B_k；分开的真实产出位置不能因为内容相同被去掉。
跨 rank 逻辑输出按归属计一次；设备资源分析则保留 rank 维度，不能把资源工作也一起删除。
多副本或多 DP 组需先定义服务总体边界和逻辑轮身份，再决定 K 与 N_B 如何汇总。

同一主机也要确认客户端单调时钟与 profiler 设备/host 时钟的对应关系及时间单位。
跨 host 时间先校准或用已验证的关联机制；保存偏移、误差范围和可比较的精度。
未经校准的时间差不能当排队/等待时长，小于对齐误差的差异不能当精确机制证据。
所有计数和比值注明归属窗口；轮跨边界时按既定规则处理，不临时选择有利部分。
短 trace 的输出必须按同窗口提取，并连接最终请求状态；观察到提交不等于最终成功。
不能以完整运行的 N_Y 除短 trace 时间，也不能跨不同运行拼出五因子精确连乘。
代表性短 trace 可解释某阶段；外推到完整运行只能标 estimated 并说明代表性与误差。
profiling 运行与关闭 profiling 的计分运行分开保存身份；两者比较用于诊断，不混成同次总账。

## 6. 用区间并集建立时间观察量

先选明确 scope，例如某 rank 的全部相关设备 stream，或经对齐的指定 rank 集合。
对选定窗口裁剪事件，加入窗口首尾端点；同类区间先取并集，再计算交集与补集。
设 C 为所观测计算活动并集、M 为所观测通信活动并集，记录秒数：

```text
compute_only = |C \ M|       communication_only = |M \ C|
overlap      = |C ∩ M|       neither            = |window \ (C ∪ M)|
T_window = compute_only + communication_only + overlap + neither
```

若通信 kernel 同时出现在算子表和通信表中，先解决重复分类，不能重复加时。
跨 rank 并集表示选定 rank 中“至少一个有该活动”的墙钟覆盖，不是资源累计时长。
跨 rank 求和则是另一种资源量；须保留单位和分母，不能除单窗口后称关键路径百分比。
neither 仅表示所选活动集合未覆盖；可能有 host 工作、未跟踪事件、等待或采集缺失。
通信持续时间可能含等其他 rank，overlap 也不自动代表通信完全隐藏或竞争可以忽略。
四类时间不直接给出唯一根因或可回收时间；端到端关键路径仍需依赖、释放与资源串行关系。

PMU 只按当前 Ascend 产品、驱动/CANN、profiler 入口和真实开关核验，不照搬其他设备列名。
记录实际导出字段、事件/计数器定义与聚合公式；未采到就写 unavailable，不用通用占比补齐。
流量/带宽分析需要匹配窗口的实际流量和时间，内存分配量、权重文件大小不等于实际读写流量。

## 7. 检查账本一致性，选择下一动作

先核对 `N_Y/T`；能用轮次细分时检查 `sum(Y_k)=N_Y`、`sum(B_k)=N_B` 及计数包含关系。
计算五因子连乘残差，写入 reconciliation；不符时先查窗口、粒度、遗漏与重复，不能调数凑齐。
若五项均由同一组总数派生，连乘约消必然得到 N_Y/T；零残差仅是算术一致，不能独立证明计数或窗口正确。
必须另查逐输出唯一键、逐轮参与原件、停止/终态关联，并与客户端总账交叉核验；保存独立检查依据和缺口，未完成时不得把整体 reconciliation 标为通过。
区间四分量应覆盖所定义 T_window；它与客户端 T 不同就分别记录，不能强行对齐数值。
实际输出、停止行为或质量发生变化时，先说明任务产出变化，再评价 token/s 的执行收益。

从账本挑选 bottleneck_candidates，每项包含观察、竞争解释、target_factor 和所缺证据。
按“可能改变决策的程度、收益空间、采集/实验成本、风险、可逆性”排序，不机械追最大占比。
下一动作可为重算已有数据、定向 profiling、补语义标记，或一个低成本受控干预。
干预本身可以检验假设；不要求开展实验前先完成唯一瓶颈证明或全部 PMU 精测。
若候选效果成立但中间信号不支持解释，效果和机制分别记录，并更新竞争假设。

## 8. 按目标因子和机制查询 KB，保留非参数路线

识别限制形态后，用 `target_factor` 与 `mechanism` 描述查询意图，按 [知识工作流](../../knowledge/references/workflow.md) 检索。
两者是候选记录字段，不假定当前 query.py 或参数卡已有同名可筛选列。
把意图转为实际支持的名称/分类/全文查询，核对卡片与当前部署源码，保存命令和命中来源。
KB 可帮助解释原始事件与分支，但建议值和 performance_impact 不能反过来证明当前瓶颈。
缺卡可定向查源码，或向协调者返回知识建设建议；查询不隐式触发建设。非参数优化也进入相同候选队列，不受参数库范围限制。

| 证据指向的限制 | 可检索或设计的动作分支 | 至少核验的副作用 |
|---|---|---|
| 实际参与/调度受限 | 调度预算、KV 策略、准入或调度代码 | 每轮代价、抢占、内存与尾时延 |
| 投机有效产出不足 | 草拟/验证策略、长度与实现 | 接受/停止保留、轮代价、质量与失败 |
| 图回退或提交开销 | 图配置、捕获范围、shape 分派或代码路径 | 编译/内存成本、错误路径与小负载回归 |
| 算子/数据流代价 | 算子选择、融合、布局、内核或代码实现 | 数值质量、真实流量、资源竞争与适用 shape |
| 分布式等待或通信代价 | 通信配置、拓扑/并行布局、分组、重叠或负载分配 | 同步等待、其他 rank 代价、内存与正确性 |
| host/供给受限 | 客户端发压、服务提交、异步队列或数据处理代码 | 发送真实性、排队、CPU/内存及服务侧实际收益 |

这些是候选分支，不是“观察一种现象就必须修改某参数”的映射表。

## 9. 交付假设与鉴别建议

按 [诊断记录](records.md) 返回观察、竞争解释、目标因子、预期机制信号和证伪条件。
动作的完整正负预测、变更依赖、实验设计、配置生效和回退由 [optimize 实验契约](../../optimize/references/experiment_contract.md) 维护；效果与保护场景由 [evaluate](../../evaluate/references/validation.md) 评估。
干预建议交协调者安排，不隐式启动服务或后续模块。新实验返回后更新局部 ledger 与假设，协调者维护全局候选队列与基线；正负结果都可作为待审阅的知识反馈。

## 10. 两个教学例子

例一：假设输出计数、成功边界、质量、负载和完整逻辑轮定义可比，Y_bar 从 2 增至 2.6 token/轮。
tau 同时从 10 ms 增至 12 ms，故 X 从 200 增至约 216.67 token/s，净增长 `1.30/1.20-1≈8.33%`。
30% 的产出增长被 20% 的完成间隔增长部分抵消；不能写成吞吐增长 30% 或相减得到 10%。
这只说明该假设下的净效果；真实实验仍要解释输出长度、停止、质量与各场景约束。

例二：某 rank 的 100 ms 短窗中，C 覆盖 60 ms、M 覆盖 30 ms、重叠 20 ms。
四分量为计算独占 40、通信独占 10、重叠 20、未覆盖 30 ms，合计 100 ms。
不能据此称“通信瓶颈占 30%，消除通信必提速 30%”，也不能将未覆盖 30 ms 全归 host。
可先提出通信传输、等待慢 rank、供给缺口和漏采等解释，补相关 rank/host/语义关联证据。
该短窗与完整 benchmark 分别记账；只有同窗同范围的数据才能相互约消，优化效果最终用完整实验验证。
