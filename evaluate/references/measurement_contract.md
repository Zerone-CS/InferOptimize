# 测量契约与原子记账

本文件由 evaluate 维护并公开，规定本工作流使用的计数，不声称 vLLM 或 msprof 原生提供同名字段。
消费者固定本文件版本或内容 hash；本任务的输出、成功、窗口等具体选择另存计量契约，不能在比较中静默改换。
先保证完整运行的输出和时间能够对账，再按假设补充内部因子。

## 1. 先选目标与窗口

| 目标 | 比较方式 | 必须保留的约束 |
|---|---|---|
| 固定请求集吞吐 | 同一请求文件和输出策略下，比较 `N_Y/T` 与完成时间 T | 输出实际数量/分布、成功率、质量、时延 |
| 固定到达负载体验 | 同到达表比较吞吐、TTFT/ITL/E2E、错误和 goodput | 发送滞后、队列、SLO 定义 |
| 受约束服务容量 | 扫描到达率/并发，寻找满足约束的可持续区间 | 稳态/队列趋势、错误率、质量、时延与资源 |

默认完整批次窗口：warmup 完成且系统排空后，从契约规定的投递起点开始，
到该批次全部请求成功、失败或按既定超时终止为止。
`T = t_end - t_start`，使用同一单调时钟，单位秒。窗口内排队、prefill、
计算、通信、空闲、失败处理、编译和收尾都不能删去。

稳定窗口也可使用，但必须另定跨界请求/输出的归属和删失处理，不与完整批次公式混用。
不能用短 trace 的时间除整个 benchmark 的输出数。

## 2. 输出总账

有效输出默认指最终成功请求中，按固定计数规则保留的新输出位置。
若“成功”还要求 SLO/质量，另行命名并报告 goodput 的筛选规则，不能默默改变吞吐定义。
同一服务端成功与客户端接收成功可能不同，契约必须选择计分边界。

`N_Y = sum(success_i × output_tokens_i)`，`X_out = N_Y / T`。

- `success_i`：第 i 个请求按约定状态最终成功为 1，否则为 0。
- `output_tokens_i`：该请求实际保留的输出 token 数，来自经验证的用量字段或生成 token ID。
- 请求若产生部分输出后失败，默认不贡献 N_Y；已消耗的时间保留。
- `max_tokens`、请求长度设定值、输入 token、SSE chunk 数、非空字符串数不是实测输出量。
- 缺少实际输出计数时标 unknown，不用 `成功数×max_tokens` 补齐。
- 声称固定生成长度的测试仍需核对 EOS、停止字符串、截断及失败，不假定每条都达上限。
- EOS/特殊 token/停止字符串如何计数写入契约。服务端用量与客户端重分词分开报告。
- 重分词可能改变 token 边界；未经验证映射，不能与逐生成位置计数混合做精确分解。

质量或停止行为改变会改变实际输出长度。相同 prompt 和 max_tokens 不保证任务产出相同；
应报告输出长度分布和质量，不能把更冗长回答带来的 token/s 增长全归为执行加速。

## 3. 需要逐步解释时，再下钻分子

选择完整逻辑产出轮 k：例如一次普通解码轮，或包含草拟、验证、停止处理的完整投机轮。
给每个输出位置一个唯一键 `(request_id, sequence_id, output_position)`。

`z_kij` 在序列 i 的位置 j 按计数规则保留且首次提交归属于轮 k 时为 1，否则为 0。
同一位置跨轮最多计一次；相同 token ID 出现在两个不同位置时分别计数。
`w_i` 表示该序列所属请求最终成功；请求多输出时按契约处理每条序列。

```text
g_ki = sum_j z_kij
Y_k = sum_i w_i × g_ki
N_Y = sum_k Y_k
X_out = N_Y / T = (N_Y/K) × (K/T) = Y_bar / tau
tau = T/K
```

必须让全部计分输出唯一归属于这些轮，等式才是精确对账。
若流程存在并发/流水，`K/T` 是完成速率，`tau` 是有效完成间隔；
它不是各逻辑轮生命周期的平均值。各轮重叠时不能相加生命周期得到 T。
即使轮串行，计分窗口内的开头/间隙/收尾也不能凭空消失，应纳入 T 或显式列为其他时间。
K=0 时只报告 `N_Y/T`，不计算含 K 的比值。

`B_k` 是完整轮 k 中实际参与的不同序列数，不是客户端并发、Running、配置上限或 padded shape。
若该轮内多次调用同一序列，B_k 仍按本定义只记一次；工作次数另记。

投机诊断时可进一步记录以下总数，均来自同一运行和窗口：

| 符号 | 定义 |
|---|---|
| N_B | `sum_k B_k`，实际序列参与次数 |
| N_G | 算法接受/采样产生、尚未做最终停止和计数筛选的唯一逻辑输出数 |
| N_C | 停止和计数筛选后保留的输出数，尚未剔除最终失败请求 |
| N_Y | N_C 中最终成功请求贡献的输出数 |

所有分母非零且计数包含关系成立时：

```text
X_out = (K/T) × (N_B/K) × (N_G/N_B) × (N_C/N_G) × (N_Y/N_C)
```

这是记账恒等式，不表示因子独立，也不提供唯一瓶颈结论。
`N_Y/N_C` 是按 token 加权的成功保留比例，不是请求成功率。
普通输出、接受草稿、拒绝处修正、全接受后的额外输出须按算法和版本定义；
不能把“接受数+1”无条件当作停止后有效输出。prefill 中间块可以贡献零输出。
被拒绝草稿、padding、prompt、重算以及 TP rank 的重复计算均不增加 N_Y。

## 4. 分母如何记账

将已记录事件端点裁剪到分析窗口，显式加入窗口起点和终点，再去重、排序为 `u_0...u_m`。
即使整个窗口没有事件，也保留这两个边界，使首尾及无事件区间仍被完整覆盖。
相邻区间 `delta_r = u_(r+1)-u_r` 互不重叠，求和等于完整分析窗口长度。
同类活动先取区间并集，再计算重叠：

```text
T_window = compute_only + communication_only + overlap + neither
```

这四项是对所观察活动集合的分类，不是四个可独立消除的成本。
例：计算覆盖 60 ms、通信覆盖 30 ms、两者重叠 20 ms、二者均未覆盖 30 ms，
窗口是 `60+30-20+30=100 ms`，不是 120 ms。
未覆盖区间不能直接改名“CPU 开销”；应检查 host 活动、供给、同步、I/O 和采集缺失。

关键路径需要数据依赖、资源串行约束、释放条件和等待关系。缺少依赖的时间线只能支持局部判断。
通信持续时间可能含等其他 rank 的时间，不能全当纯传输；异步 API 返回也不代表设备完成。
累计 kernel 时间、单 rank 占比、设备利用率都不能直接替代端到端 T。

## 5. 供给和时延口径

- `lambda_target`：计划到达率，req/s；`lambda_sent`：实际发送率，req/s。
- `X_req`：成功完成请求数/T，req/s；`X_out`：有效输出 token/s。
- `C_client`：客户端并发上限；`L_inflight`：实际在途请求数；二者也不必相等。
- 稳态、边界效应小且请求几乎全成功时，`X_req ≈ lambda_sent`，
  `X_out ≈ lambda_sent × 平均有效输出长度`。供给受限不等于指标无效。
- Little 定律使用同一系统边界和同一请求群体的长期平均 `L=lambda_eff×W`。
  含失败的在途数不能与只含成功的离开率混用；它不能从总在途数单独求服务端排队深度。
- TTFT、ITL、TPOT、E2E 分别记录定义、样本和统计量，不能互相替代。
  多 token chunk 的到达间隔不是逐 token ITL；由 chunk 估算时说明算法与局限。

## 6. 哪些因子来自哪里

| 数据层 | 可支持内容 | 不能仅凭这一层保证 |
|---|---|---|
| 客户端/benchmark | 完整窗口、发送/完成、输出用量、错误、体验时延 | 实际调度 batch、接受结果、设备等待原因 |
| 引擎语义日志 | 轮次、序列参与、接受/采样、停止原因、KV/调度原因 | 完整设备执行代价、客户端是否收全 |
| msprof/框架 profiler | 按采集能力提供 kernel/API/通信/host 事件、计数器 | 有效输出量、最终请求状态、完整因果依赖 |

实际导出字段依版本、产品、开关和采集入口检查。常规 msprof 不自动反演业务计数。
自定义标记可以连接 run/request/sequence/step，但开启标记开关不会补回历史运行中未记录的数据。
跨 host 时钟先校准或使用已验证的关联方式；不得假定各机器原始时间戳可直接相减。
短 profiling 窗口要连接后续最终状态；跨运行数据只能做对照，不可乘成“精确还原”的吞吐。
